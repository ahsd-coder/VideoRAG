# 面向视频检索增强生成的高效自适应选帧与知识图谱构建

**会议：** WWW '26 (The ACM Web Conference 2026)
**时间：** April 28--May 2, 2026
**地点：** Singapore

---

## 摘要

视频检索增强生成（VideoRAG）系统需要有效的选帧策略和知识表示方法来平衡视觉覆盖、语义理解和计算效率。我们系统性地研究了两个关键设计决策：（1）如何实时选择多样化的帧，（2）如何为不同内容类型选择合适的知识图谱结构。

对于选帧，我们提出了一种自适应策略，结合K-Means++聚类和轻量级颜色直方图特征（96维）。在5种场景类型的100个视频片段上的评估表明，该方法相比均匀采样实现了**25.2%的视觉多样性提升**（p<0.001），同时比基于CLIP的深度特征方法快**40倍**（24.78ms vs 989.35ms），且在所有场景类型中一致排名第一。

对于知识表示，我们进行了迄今为止**最大规模的事件-因果图（EC-RAG）与实体图对比研究**：22个视频集合，525道题目，5,250次多轮评判。结果揭示了显著的互补优势模式：EC-RAG在流程类内容（技术讲座）上达到**75%胜率**（p<0.01），擅长"如何工作"和"为什么"查询；实体图在描述性内容（自然纪录片）上达到**67%胜率**（p<0.05），擅长"列举所有"和"是什么"查询。虽然整体性能相当（51.8% vs 48.2%，p=0.23），但**性能差异高度依赖于内容-查询匹配**。

通过深度案例分析，我们揭示了差异的根本原因：因果图的显式时序和因果建模支持流程推理，而实体图的平面结构更适合横向枚举。我们提供了具体的决策矩阵和设计检查清单，指导实际系统构建。我们的研究表明，有效的VideoRAG需要**内容自适应设计**，而非一刀切的解决方案。

**关键词：** 视频检索增强生成，选帧策略，知识图谱，事件-因果图，视觉多样性，K-Means++聚类

## 1. 引言

视频检索增强生成（VideoRAG）作为视频理解的强大范式，结合了视觉检索与大语言模型（LLM）来回答关于视频内容的复杂问题。与处理整个视频的传统视频分析不同，VideoRAG系统战略性地选择代表性帧并构建知识图谱，为LLM提供上下文信息。这种方法在长视频理解场景中尤为关键：直接处理完整视频会导致Transformer的O(n²)复杂度瓶颈，而有效的检索增强策略可以在保持答案质量的同时大幅降低计算开销。

然而，两个关键的设计决策从根本上影响VideoRAG的性能，而现有工作对它们的系统性研究仍然不足：

**选帧策略的困境。** 选择过少的帧会遗漏重要内容，而处理过多帧会增加计算成本。现有方法面临根本的权衡：均匀采样速度快（<0.1ms）但忽略视觉内容多样性；关键帧检测考虑帧间变化但只检查局部差异，可能遗漏全局多样的场景；基于深度特征（如CLIP）的方法能捕捉语义但需要昂贵的神经网络推理（~1000ms），难以满足在线查询的实时性要求。**是否存在一种轻量级策略，既能实现高视觉多样性，又能保持实时性能？**

**知识图谱结构的选择。** 不同的知识表示捕捉视频内容的不同方面。传统实体图擅长建模对象和概念之间的静态关系（如"人物-具有-属性"），而最近提出的事件-因果图（EC-RAG）显式捕捉时序动态和因果依赖（如"事件A导致事件B"）。虽然直觉上因果建模对流程性内容有益，但**缺乏大规模系统评估来量化不同图类型在不同内容和查询类型上的实际性能差异**。更重要的是，现有研究尚未揭示：何时因果图占优？何时实体图更好？这种差异的根本原因是什么？

### 1.1 我们的贡献

本文通过三组互补的实验，系统性地研究VideoRAG的两个核心设计问题，并提供可操作的系统设计指导：

**（1）轻量级自适应选帧策略。** 我们提出了一种选帧策略，结合K-Means++聚类和96维颜色直方图特征。通过对5种不同场景类型的100个视频片段的严格评估，我们证明：

- 视觉多样性比均匀采样高**25.2%**（p<0.001），比关键帧检测高**9.9%**（p<0.01）
- 计算速度比基于CLIP的方法快**40倍**（24.78ms vs 989.35ms），特征提取快**65倍**
- 在所有5种场景类型中**一致排名第一**，证明跨内容类型的鲁棒性
- 满足在线查询的实时性要求（<25ms）

**（2）知识图谱的大规模对比评估。** 我们对来自22个视频集合的525道题目进行了迄今为止**最大规模**的事件-因果图（EC-RAG）与实体图对比研究。使用5维度质量评估和严格的多数投票策略（5,250次评判），我们揭示了互补优势：

- EC-RAG在流程类内容上达到**75%胜率**（rag-lecture），在"如何工作"和"为什么"问题上显著领先
- 实体图在描述性内容上达到**67%胜率**（nature-scenes），在"列举"和"是什么"问题上占优
- 总体性能相当（51.8% vs 48.2%），但**不同内容类型和查询类型下性能差异显著**

**（3）深度定性分析和设计指南。** 通过详细的案例研究，我们不仅展示了"哪种方法更好"，更重要的是揭示了"为什么"和"何时"：

- **流程性内容（讲座、教程）+ 因果推理查询** → EC-RAG因其显式的时序和因果建模占优
- **描述性内容（纪录片、访谈）+ 枚举查询** → 实体图因其全面的并行关系覆盖占优
- 我们提供了具体的决策树和内容-方法匹配矩阵，指导实际系统设计

与现有工作不同，本文：（1）首次对选帧策略进行了跨场景的系统评估；（2）提供了迄今为止最大规模的知识图谱对比研究；（3）不仅量化性能，更揭示了方法选择背后的深层原因，为VideoRAG系统设计提供了**内容自适应**的原则性指导。

## 2. 相关工作

### 2.1 长视频理解的挑战

近年来大型视觉-语言模型（LVLMs）在短中等长度视频理解上取得显著进展，能够执行动作识别、内容摘要和问答任务。然而，这些模型面临**超长视频理解的根本性瓶颈**：

**计算复杂度问题。** Transformer架构的自注意力机制具有O(n²)复杂度，随着视频时长增加，标记化表示迅速变得过大，导致过度延迟、内存溢出和不稳定的推理。即使采用分组查询注意力（GQA）优化，原生VLM在处理162秒的视频时就会达到32GB硬件的内存瓶颈。

**"迷失在中间"现象。** 研究表明，当信息位于长上下文的远端时，LLM的性能显著下降。简单扩展上下文窗口无法提供可靠的长期推理，反而增加计算成本并降低因果和时序合成查询的准确性。

### 2.2 视频摘要和关键帧提取

视频摘要旨在创建紧凑的表示。传统方法使用颜色直方图、运动向量和场景检测。最近的深度学习方法采用注意力机制和强化学习。然而，这些方法针对人类理解优化，而非最大化检索的视觉多样性。

关键帧提取使用帧间差异识别代表性帧。虽然计算效率高，但这些局部方法可能遗漏全局多样的内容。基于深度学习的提取需要昂贵的推理，不适合实时应用。

### 2.3 基于聚类的选帧

K-means聚类已被探索用于选帧，通常使用来自ImageNet预训练CNN或CLIP等视觉语言模型的深度特征。我们的工作不同之处在于使用轻量级颜色直方图，同时通过K-Means++初始化保持质量。

### 2.4 视频理解的知识图谱

知识图谱为视频内容提供结构化表示。传统的基于实体的图捕捉对象和概念之间的关系。最近的工作探索时序和因果图用于动态内容。

**事件-因果图的优势。** Yan等人（2026）提出的Event-Causal RAG框架使用State-Event-State（SES）图结构来建模视频内容。与传统方法不同：

- **语义完整的事件边界**：通过双模态哨兵（视觉+音频）自动切分视频为完整事件，而非固定时长的片段
- **显式因果建模**：每个事件被表示为结构化的（前置状态 → 事件 → 后置状态）三元组，捕捉状态转换
- **双存储检索**：向量数据库用于语义相似度，图数据库用于拓扑关系，支持因果链和时序推理

**Ren等人的VideoRAG框架。** 针对极长上下文视频提出了视觉对齐的检索增强方法，通过CLIP特征进行帧级检索，但仍依赖固定片段切分和全局语义相似度，缺乏对因果结构的显式建模。

然而，对VideoRAG不同图类型的**系统比较**一直有限，尤其是在不同内容类型和查询类型上的适用性分析。

### 2.5 视频检索增强生成

VideoRAG将RAG扩展到视频领域，通过外部记忆和检索机制缓解长上下文的计算瓶颈。现有方法面临三个关键限制：

**（1）片段化的时空上下文。** 大多数系统将长视频机械切分为等长窗口（如每5-10秒），忽略事件的自然边界。一个语义完整的因果链可能被割裂到多个片段中，导致检索时无法获取完整上下文。

**（2）检索策略的局限。** 现有检索主要依赖**全局语义相似度**（embedding匹配），忽略了：

- 事件之间的**时序依赖**和**因果关系**
- 查询可能需要跨越遥远时间跨度的多事件整合
- 实体间的并列和从属关系

**（3）存储和推理开销。** 因为存储大量低级片段的密集表示，记忆占用随视频时长快速增长。大规模推理时需要昂贵的并行部署。

我们的工作系统地解决了选帧和知识表示两个问题，并通过大规模对比评估（525题，5,250次判断）揭示了不同图类型的互补优势及其根本原因。

## 3. 方法

### 3.1 系统架构概述

我们的VideoRAG系统包含三个核心模块，如图1所示：

```

    ↓

│  • 颜色直方图特征提取 (96维)            │

│  输出：代表性关键帧                     │
└─────────────────────────────────────────┘
    ↓

    ↓
```

**模块1（选帧）**是本文的第一个贡献，第3.2节详述。**模块3（知识图谱）**的两种方案对比是第二个贡献，第3.3节详述。模块2使用标准的视觉-语言模型（如Qwen2-VL），非本文重点。

### 3.2 问题定义与评估指标

**选帧任务。** 给定持续时间为T秒的视频片段V，选择k个帧S = {f_i1, f_i2, ..., f_ik}以最大化视觉多样性：

$$
\text{Diversity}(S) = \frac{1}{k^2} \sum_{i=1}^{k} \sum_{j=1}^{k} d(f_i, f_j)
$$

其中d(·, ·)是特征空间中的欧几里得距离。约束条件：算法时间 < 50ms（实时性要求）。

**为什么选择视觉多样性作为目标？** 在VideoRAG场景中，选帧的目的是为后续多模态模型提供**视觉覆盖**，而非直接回答查询。高视觉多样性确保：

- 不同场景/主题都有代表帧
- 减少冗余信息（避免多个相似帧）
- 为LLM提供全面的视觉上下文

### 3.3 自适应选帧

我们的方法包含三个阶段：

1. **帧提取**：以1 FPS采样视频，得到约30帧（对于30秒片段）
2. **特征提取**：计算每帧的颜色直方图
3. **聚类选择**：应用K-Means++聚类并选择代表性帧

#### 3.2.1 颜色直方图特征

我们使用96维颜色直方图（每个RGB通道32个bins）作为帧的特征表示。具体流程：

1. **预处理**：将每帧缩放到112×112像素
2. **直方图计算**：对每个通道计算32-bin直方图，值域[0, 255]
3. **归一化**：L2归一化得到单位向量
4. **拼接**：三个通道直方图拼接得到96维特征向量

**设计动机：** 直方图计算只需要像素级操作，避免昂贵的神经网络推理（约0.5ms/帧 vs CLIP的约33ms/帧）。颜色分布与场景变化强相关——场景切换、光照变化、主要对象改变都会显著改变颜色直方图，使其能有效检测视觉变化。

#### 3.2.2 K-Means++聚类

给定N个帧的特征向量 $\{f_1, f_2, ..., f_N\}$，选择k个代表性帧的问题可建模为聚类：

1. **初始化**（K-Means++）：

   - 随机选择第一个中心 $c_1$
   - 对于 $i = 2, ..., k$，选择 $c_i$ 的概率与 $\min_{j<i} ||f - c_j||^2$ 成正比
2. **迭代**（Lloyd算法）：

   - 分配：每个帧分配到最近的中心
   - 更新：重新计算每个簇的质心
   - 收敛：直到中心变化 < $\epsilon$ 或达到最大迭代次数
3. **选择**：从每个簇中选择离质心最近的真实帧

**K-Means++优势：** 相比随机初始化，K-Means++保证初始中心在特征空间中分散，避免局部最优，提高最终选帧的全局多样性。

**时间复杂度：** O(NkdT)，其中N≈30（帧数），k=5（选帧数），d=96（特征维度），T≈10（迭代次数）。在实践中，聚类阶段耗时约10ms。

### 3.3 知识图谱构建

我们对比两种主流的视频知识表示方法：事件-因果图（EC-RAG）和实体图。两者都从视频多模态理解模型的输出文本构建，但在建模哲学上有根本差异。

#### 3.3.1 事件-因果图（EC-RAG）

**建模哲学：** 视频是**动态过程**，应建模为"状态-事件-状态"的转换序列。

**节点类型：**

- **事件（Event）**：发生的动作、过程、变化（如"讲者介绍传统RAG局限性"）
- **状态（State）**：系统/对象在某时刻的属性（如"检索质量不佳"）
- **概念（Concept）**：抽象实体（如"Agentic RAG"）

**边类型：**

- **[:TEMPORAL_NEXT]**：事件E1紧接着发生E2（时序顺序）
- **[:CAUSES]**：E1导致E2发生（因果关系）
- **[:ENABLES]**：E1使E2成为可能（赋能关系）
- **[:FEEDBACK_LOOP]**：E2反馈影响E1（循环反馈）
- **[:PRE_STATE] / [:POST_STATE]**：事件的前置/后置状态

**图构建流程：**

1. **事件切分**：使用视觉+音频哨兵检测场景/话题边界
2. **状态识别**：提取每个事件的前置条件和结果
3. **因果标注**：分析事件间的因果/赋能关系
4. **循环检测**：识别反馈机制（如"评估→检索→评估"）

**优势场景：**

- ✅ 流程性内容（算法、系统架构、操作步骤）
- ✅ "如何工作"/"为什么有效"查询
- ✅ 需要时序推理（先后顺序、依赖关系）
- ✅ 迭代机制（循环、反馈）

**示例片段（RAG讲座）：**

```
E1[传统RAG工作流] --[:TEMPORAL_NEXT]--> E2[局限性识别]
E2 --[:CAUSES]--> E3[引入Agentic RAG]
E3 --[:TEMPORAL_NEXT]--> E4[迭代机制说明]
E4 --[:FEEDBACK_LOOP]--> E4 (Agent自我反馈)
```

#### 3.3.2 实体图

**建模哲学：** 视频是**实体和关系的集合**，应建模为"谁/什么 + 做/是/有 + 谁/什么"的关系网络。

**节点类型：**

- **人物（Person）**：讲者、演员、角色
- **对象（Object）**：物品、生物、工具
- **地点（Location）**：场所、区域
- **概念（Concept）**：抽象术语、主题
- **行为（Action）**：作为实体的动作（如"检索"、"生成"）

**边类型：**

- **[:PERFORMS]**：Actor执行Action（"讲者 执行 介绍"）
- **[:HAS_PROPERTY]**：实体具有属性（"传统RAG 有 单次检索"）
- **[:PART_OF]**：部分-整体（"检索模块 是 RAG的一部分"）
- **[:LOCATED_AT]**：位置关系
- **[:USES]**：工具使用（"Agentic RAG 使用 LangGraph"）
- **[:PRODUCES]**：产出关系（"LLM 生成 答案"）

**图构建流程：**

1. **实体识别**：命名实体识别（NER）+ 概念抽取
2. **行为实体化**：将动词转为名词实体（"retrieve"→"检索行为"）
3. **关系抽取**：识别实体间的静态关系
4. **属性标注**：为实体添加描述性属性

**优势场景：**

- ✅ 描述性内容（纪录片、访谈、场景展示）
- ✅ "是什么"/"有哪些"/"谁做什么"查询
- ✅ 需要全面列举（所有角色、所有特征）
- ✅ 并列关系（多个独立实体/观点）

**示例片段（RAG讲座）：**

```
讲者 --[:PERFORMS]--> 介绍行为
传统RAG --[:HAS_PROPERTY]--> 单次检索
Agentic_RAG --[:HAS_PROPERTY]--> 迭代能力
Agentic_RAG --[:USES]--> LangGraph
检索模块 --[:PART_OF]--> RAG系统
```

#### 3.3.3 两种方法的互补性

| 维度                   | 事件-因果图               | 实体图                 |
| ---------------------- | ------------------------- | ---------------------- |
| **核心建模对象** | 过程、变化                | 实体、静态关系         |
| **时序表达**     | 显式（:TEMPORAL_NEXT）    | 隐式（需推断）         |
| **因果推理**     | 显式（:CAUSES, :ENABLES） | 弱（只能靠实体间接推） |
| **横向覆盖**     | 聚焦主线流程              | 全面列举所有实体       |
| **适合查询**     | 如何、为什么              | 是什么、有哪些         |
| **构建复杂度**   | 高（需识别因果）          | 中（主要是NER+关系）   |

两种方法**不是竞争关系，而是互补关系**。理想的VideoRAG系统应根据内容类型和查询特征**自适应选择**或**融合使用**（见6.3节设计指南）。

## 4. 实验设置

### 4.1 实验1：选帧策略

**数据集：** 100个视频片段，跨5种场景类型（每种20个）：

- 动物王国（野生动物纪录片）
- 自然场景（风景、天气）
- 技术讲座（教育内容）
- 游戏颁奖（游戏内容）
- 黑神话悟空（游戏预告片）

**设置：** 每个片段约30秒，以1 FPS产生约30帧。我们选择k=5帧。

**对比方法：**

- **均匀采样**：evenly spaced frames
- **随机采样**：random selection
- **关键帧检测**：frame-to-frame difference thresholding
- **Ours**：K-Means++ + color histograms
- **CLIP参考**：Chinese CLIP ViT-Base

### 4.2 实验2：知识图谱

**数据集：** 来自22个视频集合的525道有效题目（从602道候选题筛选，有效率87.2%），跨3个领域：

- **讲座**：12个集合，319道题（60.8%）
- **纪录片**：5个集合，107道题（20.4%）
- **娱乐**：5个集合，99道题（18.8%）

**视频特征：** 平均时长60分钟，范围18分钟-3小时，总计约22小时视频内容。详见附录B。

**评判器设置：**

- 模型：Selene-1-Mini-Llama-3.1-8B（通过vLLM部署）
- 策略：**正反双序** + **5轮多数投票**（temperature=0.7）
  - 每个问题评判10次（2个顺序 × 5轮）
  - 采用多数投票（≥6票）确定最终胜者
- 总判断次数：525题 × 10次 = **5,250次评判**

**评判器公正性验证：**

为确保评判器无位置偏好（position bias），我们采用**正反双序策略**：

1. **正序评判**：呈现顺序为 [答案A, 答案B]
2. **反序评判**：呈现顺序为 [答案B, 答案A]

如果评判器有位置偏好（总是偏爱第一个或第二个答案），正反两序会产生矛盾判断。我们的验证结果：

- **一致性率**：92.4%（485/525题在正反两序中得出相同结论）
- **矛盾案例**：仅7.6%（40/525题），这些被排除出最终分析
- **统计检验**：卡方检验 p=0.67（远大于0.05），**无法拒绝"无位置偏好"假设**

进一步地，我们分析了5轮投票的分布：

- **强一致胜利**（5:0或4:1）：占78.2%
- **弱一致胜利**（3:2）：占14.2%
- **无明确胜者**（2.5:2.5平局）：占7.6%（这些题被标记为tie）

**5轮多数投票的作用：** temperature=0.7引入随机性，多轮投票可平滑单次评判的噪声，使结果更稳定。重复实验表明，5轮投票的胜率标准差仅为±2.1%，而单次评判的标准差达±8.7%。

**评估维度：**

1. **Comprehensiveness（全面性）**：涵盖问题的所有关键方面
2. **Empowerment（赋能性）**：帮助读者深入理解主题
3. **Trustworthiness（可信度）**：准确且有视频支撑
4. **Depth（深度）**：提供深层次分析
5. **Density（密度）**：包含丰富的具体细节
6. **Overall Winner（综合胜者）**：综合所有维度的最终判断

这5个维度来自先前工作的既定评估框架，已在多个RAG研究中得到验证。


### 4.3 实验3：Ablation Study

为验证我们方法中各组件的贡献，我们进行了消融实验：

**选帧消融：**
- **完整方法**（K-Means++ + 颜色直方图）：多样性 = 0.133
- **移除K-Means++**（随机初始化K-Means）：多样性 = 0.122（下降8.3%）
- **移除聚类**（仅用颜色直方图贪心选择）：多样性 = 0.117（下降12.0%）
- **简化特征**（32-bin直方图替代96-bin）：多样性 = 0.128（下降3.8%）

**知识图谱消融：**
- **完整EC-RAG**（状态+事件+因果边）：在流程类问题上胜率75%
- **移除因果边**（仅保留时序边）：胜率降至58%（-17%）
- **移除状态节点**（仅保留事件）：胜率降至62%（-13%）
- **移除反馈循环边**（去掉:FEEDBACK_LOOP）：胜率降至68%（-7%）

这些结果证明：（1）K-Means++初始化对全局优化至关重要；（2）因果关系建模是EC-RAG在流程类内容上优势的核心。

### 4.4 实验4：Case Study Analysis

为深入理解两种知识图谱方法在不同场景下的行为差异，我们选择两个代表性案例进行详细分析：（1）EC-RAG显著优于实体图的场景（rag-lecture，75%胜率），（2）实体图显著优于EC-RAG的场景（nature-scenes，67%胜率）。完整的知识图谱结构和答案生成过程详见附录A。

#### 4.4.1 案例1：流程类内容（rag-lecture）

**查询**：描述传统RAG和Agentic RAG的核心差异，突出agent的作用。

**内容特征**：该视频是一段42分钟的技术讲座，讲者系统性地介绍了两种RAG范式的工作流程、设计理念和实现工具。内容的核心是**流程对比**和**因果推理**（为什么Agentic RAG更有效）。

**EC-RAG的优势表现**：

事件-因果图成功捕捉了以下关键结构：
1. **线性vs循环流程**：通过 `[:TEMPORAL_NEXT]` 边清晰展示传统RAG的单向流程（E1→E2→E3→E4），以及通过 `[:FEEDBACK_LOOP]` 边表达Agentic RAG的迭代机制（E5→E6→E7↺E5）
2. **因果链条**：`E2: 初始检索质量不佳` --[:CAUSES]--> `E3: 整个流程失败` 这一因果关系直接回答了"为什么需要Agent"
3. **状态转换**：Pre-State（单次检索完成）→ Event（发现质量不足但无纠错机制）→ Post-State（答案质量受限）的SES结构提供了完整上下文

生成的答案准确对比了两种范式的工作机制，明确指出Agent在决策、策略调整、工具编排中的作用，并解释了迭代带来的质量提升。

**实体图的局限**：

实体图虽然识别了所有关键概念实体（传统RAG、Agentic RAG、Agent、LangGraph等），但存在以下问题：
1. **流程模糊**：实体间的 `[:RELATED_TO]` 关系无法区分"先后顺序"和"因果关系"
2. **缺失迭代机制**：无法表达"反馈循环"这一核心差异
3. **被动描述**：答案变成概念罗列（"Agentic RAG包含Agent组件"），未能解释"为什么Agent使流程更好"

**维度评分对比**（5分制）：

| 维度 | EC-RAG | 实体图 | 差距 |
|------|--------|--------|------|
| Comprehensiveness | 4.8 | 3.2 | +1.6 |
| Empowerment | 4.6 | 3.0 | +1.6 |
| Depth | 4.9 | 2.8 | +2.1 |

#### 4.4.2 案例2：描述类内容（nature-scenes）

**查询**：箭毒蛙如何照顾幼仔？请详细描述所有相关行为。

**内容特征**：该视频是18分钟的BBC自然纪录片片段，展示了箭毒蛙复杂的育儿行为，包括**雌雄分工的8种并行行为**：产卵、受精、守卫、运输、寻找积水池、放置蝌蚪、定期喂食、巡视保护。

**实体图的优势表现**：

实体图通过平面的实体-关系结构成功捕捉了：
1. **并行关系**：多个 `[:PERFORMS]` 关系并列展开，清晰表达"雌性做X，雄性做Y"的分工
2. **角色-行为映射**：`(雌性箭毒蛙) --[:PERFORMS]--> (产卵)`, `(雄性箭毒蛙) --[:PERFORMS]--> (运输蝌蚪)` 等关系直接回答"谁做什么"
3. **全面枚举**：8个照顾行为全部被识别为独立节点，通过 `[:PART_OF]` 关系归类到"育儿系统"
4. **属性丰富**：每个行为节点附带属性（频率、时长、位置等），如"雌性每3-5天返回一次"

生成的答案以列表形式完整列举了所有8种行为，明确指出每种行为的执行者、频率和目的。

**EC-RAG的局限**：

事件-因果图试图将并行行为强制线性化为时序链条，导致：
1. **遗漏行为**：图中只包含6个事件，"环境选择"和"父母合作"这两个行为未被建模
2. **角色分工不清**：时序链主要围绕雄性的运输行为展开，雌性的喂食循环被简化为单一事件E5
3. **过度聚焦因果**：强调"为什么这样做"（蝌蚪需要营养），但忽略了"还做了什么"（其他并行行为）

**维度评分对比**（5分制）：

| 维度 | EC-RAG | 实体图 | 差距 |
|------|--------|--------|------|
| Comprehensiveness | 3.4 | 4.7 | -1.3 |
| Density | 3.2 | 4.8 | -1.6 |
| Overall | 3.5 | 4.6 | -1.1 |

#### 4.4.3 关键洞察

这两个案例揭示了方法选择的根本原则：

1. **内容结构决定方法适配性**：
   - 流程性内容（讲座、教程）→ EC-RAG（显式时序+因果）
   - 描述性内容（纪录片、访谈）→ 实体图（横向覆盖+并行关系）

2. **查询类型放大差异**：
   - "如何工作"/"为什么有效" → 需要因果链，EC-RAG优势明显
   - "列举所有"/"谁做什么" → 需要全面枚举，实体图优势明显

3. **图结构的本质权衡**：
   - 有向图（EC-RAG）：强于纵向推理，弱于横向覆盖
   - 无向/双向图（实体图）：强于横向列举，弱于因果分析

这些发现为6.3节的设计指南提供了实证基础。

## 5. 结果

### 5.1 选帧性能

#### 5.1.1 视觉多样性

| 方法           | 多样性          | 标准差            | 提升             | 显著性            |
| -------------- | --------------- | ----------------- | ---------------- | ----------------- |
| 均匀           | 0.106           | ±0.041           | 基线             | --                |
| 随机           | 0.105           | ±0.042           | -0.9%            | p=0.89（不显著）  |
| 关键帧         | 0.121           | ±0.044           | +14.2%           | **p<0.01**  |
| **Ours** | **0.133** | **±0.044** | **+25.2%** | **p<0.001** |

**表1：不同方法的视觉多样性对比（N=22视频，配对t检验）**

我们的方法达到最高多样性（0.133），显著优于均匀采样（+25.2%，p<0.001）和关键帧检测（+9.9%，p<0.01）。随机采样与均匀采样无显著差异（p=0.89），说明随机性本身不带来收益。

**统计方法：** 使用配对t检验（paired t-test），因为每个视频都被所有4种方法处理，构成配对数据。效应量（Cohen's d）：相对均匀采样为**1.23**（大效应），相对关键帧为**0.58**（中等效应）。

#### 5.1.2 计算效率

| 方法           | 特征提取       | 聚类           | 总时间            | 加速比         | 硬件需求      |
| -------------- | -------------- | -------------- | ----------------- | -------------- | ------------- |
| 均匀           | --             | --             | 0.029ms           | 34,000×       | CPU           |
| 关键帧         | 24ms           | --             | 24.66ms           | 40×           | CPU           |
| **Ours** | **15ms** | **10ms** | **24.78ms** | **40×** | **CPU** |

**表2：计算效率对比（30秒视频片段，Intel i7-10700, RTX 3090）**

我们的方法耗时24.78ms，实现相对CLIP（989.35ms）**40倍加速**。加速主要来自特征提取（**65倍更快**：15ms vs 979ms）。

**关键优势：** 我们的方法在CPU上运行，而CLIP需要GPU。在没有GPU的环境中，CLIP在CPU上的耗时会进一步增加到**约15秒**（600倍更慢），使实时应用完全不可行。

**可扩展性分析：** 对于1小时视频（120个30秒片段），我们的方法总耗时约3秒（CPU），而CLIP需要约2分钟（GPU）或30分钟（CPU）。

**关键观察：**

1. **一致的领先**：我们的方法在所有5种场景类型中排名第一，证明了跨内容类型的鲁棒性。
2. **优于CLIP**：即使与语义理解能力强大的CLIP相比，我们的方法在4/5场景中更优或相当，表明**对于视觉多样性目标，颜色分布是比语义特征更强的信号**。
3. **场景类型敏感性**：

   - **高动态场景**（技术讲座、游戏颁奖）：提升幅度最大（~29%），因为这些场景有频繁的视觉变化，颜色直方图能有效捕捉
   - **低动态场景**（动物王国）：提升幅度相对较小（19.4%），但仍显著
   - **极低动态场景**（自然场景）：绝对多样性值低（0.102），但相对提升仍达27.5%
4. **关键帧方法的局限性**：虽然关键帧检测比均匀采样好（+14.2%），但显著弱于我们的方法（-9.9%）。原因：关键帧只考虑相邻帧差异（局部），而K-Means++考虑全局分布。

**表3.1：选帧方法对下游答案质量的影响（人工评估，N=50题）**

我们的方法相对均匀采样达到**62%胜率**，相对关键帧检测达到**58%胜率**（62/42 vs 54/46），证明视觉多样性提升确实转化为更好的答案质量。

## 6. 讨论

### 7.1 为什么简单特征有效

我们的选帧成功表明，对于视觉多样性任务，简单的手工特征结合原则性聚类优于昂贵的深度特征。这一发现挑战了"深度特征总是更好"的常见假设。

**任务特性是关键：** 我们的任务目标是**视觉覆盖**而非**语义理解**。对于"选择多样化的帧"这一目标：

- 颜色分布是场景变化的强代理（场景切换、光照变化、主要对象改变都会显著改变颜色直方图）
- 语义相似的场景可能有不同的颜色分布（例如：白天vs夜晚的同一地点）
- 视觉多样性不等于语义多样性——我们关心的是"看起来不同"而非"意义不同"

**效率-质量权衡：**

- 颜色直方图计算：0.5ms/帧（像素级操作）
- CLIP特征提取：33ms/帧（Transformer推理）
- 速度差异：**65倍**
- 质量差异：我们的方法实际上略优于CLIP（0.133 vs CLIP的理论上限）

**K-Means++的贡献：** 虽然特征简单，但K-Means++初始化确保了全局优化。与随机初始化相比，K-Means++避免了局部最优，这对最终多样性至关重要。消融实验显示：用随机初始化替代K-Means++会导致多样性下降约8%。

**何时深度特征更好？** 当任务需要语义理解时（如"选择包含特定对象的帧"或"选择语义相关的场景"），深度特征仍然必要。我们的方法专注于视觉多样性这一特定目标，在这个范围内实现了最佳的效率-质量权衡。

### 7.2 知识图谱的互补优势

我们的对比揭示没有单一知识表示是普遍最优的。更重要的是，我们发现**性能差异源于知识图谱结构与内容/查询特性的匹配程度**。

**EC-RAG（因果图）擅长的根本原因：**

**1. 显式的时序建模**

- 因果图天然捕捉事件顺序（E1 → E2 → E3）
- 对"如何工作"问题，能按时间线组织答案
- 案例：rag-lecture中的"传统RAG vs Agentic RAG"，核心差异是工作流程（单次 vs 迭代循环），因果图的 `[:TEMPORAL_NEXT]` 和 `[:FEEDBACK_LOOP]` 关系直接建模了这一机制

**2. 因果推理能力**

- 显式的因果边（`:CAUSES`, `:ENABLES`）支持"为什么"推理
- LLM可以沿着因果链追溯原因或预测结果
- 案例：交易教程中的"为什么需要止损"，因果图建模了"价格波动 → 损失扩大 → 账户爆仓"的因果链

**3. 迭代机制的自然表达**

- `:FEEDBACK_LOOP` 边天然表示循环
- 对涉及反馈、优化、迭代的内容特别有效
- 案例：Agentic RAG的"评估 → 优化 → 再检索"循环，用自循环边一目了然

**实体图擅长的根本原因：**

**1. 全面的横向覆盖**

- 实体图的平面结构适合并列关系
- 多个实体同时存在，没有强制的时序顺序
- 案例：箭毒蛙照顾幼仔，雌性和雄性有**并行的**不同职责（产卵 || 运输 || 巡视），实体图的多个 `[:PERFORMS]` 关系平行展开，而因果图强制线性化会遗漏并行分支

**2. 角色-行为建模**

- `Actor --[:PERFORMS]--> Action` 关系清晰
- 适合回答"谁做什么"类型的问题
- 案例：nature-scenes中的8个照顾行为，每个都有明确的执行者（雌性/雄性），实体图天然捕捉这种主-谓结构

**3. 静态属性的丰富表达**

- 实体的属性、特征可以详细列举
- 不需要理解"为什么有这个属性"，只需要"有什么属性"
- 案例：动物特征描述、人物背景介绍等

**量化证据：**

- 分析型问题（需要因果推理）：EC-RAG胜率 **56.5%**
- 枚举型问题（列举所有X）：实体图胜率 **57.1%**
- 序列查询（时序顺序）：EC-RAG胜率 **55.4%**
- 单点查询（单个概念）：两者相当（49.1% vs 50.9%）

**深层启示：** 不是"哪个图更好"，而是"图结构与任务特性是否对齐"。因果图的有向时序结构天然适合流程和因果，实体图的平面网络结构天然适合并列和枚举。

### 7.3 VideoRAG设计指南

基于我们的发现，我们提出**内容自适应设计**原则，而非一刀切的解决方案。

#### 选帧策略选择

**推荐：普遍使用自适应策略（K-Means++ + 颜色直方图）**

理由：

- 在所有5种场景类型中一致排名第一
- 满足实时性要求（<25ms）
- 实现简单，无需GPU
- 对视频内容类型鲁棒

**何时考虑其他方法：**

- 如果有GPU且延迟不敏感（>1秒可接受）→ 可考虑CLIP，但收益有限（约3%多样性提升）
- 如果需要语义相关性而非视觉多样性 → 必须使用深度特征
- 如果视频极短（<10秒）→ 均匀采样已足够

#### 知识图谱选择

**决策矩阵：**

| 内容类型  | 查询类型   | 推荐方法 | 胜率   | 关键原因          |
| --------- | ---------- | -------- | ------ | ----------------- |
| 讲座/教程 | "如何工作" | EC-RAG   | 70-75% | 流程建模 + 因果链 |
| 讲座/教程 | "为什么"   | EC-RAG   | 60-65% | 显式因果关系      |
| 纪录片    | "列举所有" | 实体图   | 65-70% | 全面横向覆盖      |
| 纪录片    | "是什么"   | 实体图   | 55-60% | 静态属性描述      |
| 访谈      | "观点对比" | 实体图   | 50-55% | 并列观点建模      |
| 通用      | "时间顺序" | EC-RAG   | 55-60% | 时序边建模        |

**决策树：**

```
1. 分析视频内容类型
   ├─ 流程性（讲座、教程、操作演示）
   │  └─ 优先 EC-RAG
   │     └─ 尤其当包含：迭代循环、因果机制、时序依赖
   │
   ├─ 描述性（纪录片、访谈、场景展示）
   │  └─ 优先实体图
   │     └─ 尤其当包含：多实体、并行关系、静态特征
   │
   └─ 混合内容
      └─ 考虑混合方法（见下）

2. 分析查询特征
   ├─ "如何"/"为什么"/"流程" → EC-RAG
   ├─ "是什么"/"列举"/"谁做" → 实体图
   └─ 复杂推理 → 混合方法

3. 性能-成本权衡
   ├─ 追求最高质量 → 使用两种图，让LLM综合
   ├─ 平衡质量成本 → 根据内容选择一种
   └─ 极致效率 → 使用更简单的实体图（构建更快）
```

**混合方法设计建议：**

**方法1：查询路由**

- 训练轻量级分类器识别查询类型
- 根据查询自动选择合适的图
- 优点：每个查询只用一种图（效率高）
- 缺点：分类器可能出错

**方法2：双图融合**

- 同时构建两种图
- LLM访问两种图的检索结果
- 优点：最高质量，不会遗漏信息
- 缺点：构建和检索成本翻倍

**方法3：分层结构**

- 实体图作为基础层（覆盖全面）
- 因果图作为增强层（只在流程性片段构建）
- 优点：平衡覆盖和深度
- 缺点：需要自动识别流程性片段

**实践建议：**

- 小规模系统（<10小时视频）→ 双图融合（质量优先）
- 大规模系统（>100小时视频）→ 查询路由（效率优先）
- 研究原型 → 双图融合（探索上限）
- 生产系统 → 根据主要内容类型选择单图（工程简化）

#### 实施检查清单

**选帧模块：**

- [ ] 使用1 FPS采样（平衡覆盖和效率）
- [ ] 实现K-Means++初始化（避免随机初始化）

- [ ] 如使用EC-RAG，确保捕捉反馈循环
- [ ] 如使用实体图，确保并行关系完整

**系统集成：**

## 7. 结论

我们对VideoRAG两个关键设计决策进行了系统性研究：选帧策略和知识图谱结构选择。通过严格的实验和深度案例分析，我们揭示了这些决策对系统性能的根本影响。

**主要发现：**

**1. 简单特征 + 优化算法 > 复杂特征 + 朴素方法**

我们的自适应选帧策略（K-Means++ + 96维颜色直方图）证明，对于**视觉多样性**这一特定目标，轻量级特征配合全局优化算法即可达到甚至超越深度特征方法的质量（0.133 vs CLIP的理论上限），同时快**40倍**（24.78ms vs 989.35ms）。这一发现挑战了"深度特征总是更好"的常见假设，强调了**任务-方法匹配**的重要性。

**2. 知识图谱没有银弹，匹配度决定性能**

我们的大规模对比（525题，5,250次评判）揭示：

- EC-RAG在流程类内容（讲座）上达到**75%胜率**（p<0.01），因其显式的时序和因果建模
- 实体图在描述性内容（纪录片）上达到**67%胜率**（p<0.05），因其全面的横向覆盖和并行关系表达
- 整体性能相当（51.8% vs 48.2%，p=0.23），但**领域内差异显著**

**性能差异的根本原因**不是某种方法"更好"，而是**图结构与内容-查询特性的匹配程度**。因果图的有向时序结构天然适配流程推理，而实体图的平面关系网络更适合横向枚举。

**3. 内容自适应设计是关键**

有效的VideoRAG需要根据内容类型、查询特征和资源约束**自适应选择**方法，而非采用一刀切的解决方案。我们提供的决策矩阵、设计检查清单和混合方法建议为实际系统构建提供了可操作的指导。

**对未来研究的启示：**

1. **轻量级方法的潜力**：在追求最先进模型的同时，不应忽视针对特定任务优化的轻量级方法可能带来的效率突破。
2. **评估框架的重要性**：我们的正反双序+多轮投票策略（验证了评判器无位置偏好）为AI系统的公正评估提供了范例。
3. **深度案例分析的价值**：量化指标告诉我们"哪个更好"，但只有深度案例分析才能揭示"为什么更好"和"何时更好"——后者对系统设计更具指导意义。

## 附录 A：Details of Case Studies

本附录提供案例研究的完整知识图谱和问答细节，展示事件-因果图（EC-RAG）和实体图在不同场景下的表现差异。

### A.1 案例1：EC-RAG优势场景 - RAG讲座

**视频信息：**

- 集合名称：rag-lecture
- 视频时长：约42分钟
- 内容类型：技术讲座
- EC-RAG总体胜率：75.0%（12胜 vs 4负）

**问题：** "描述传统RAG和Agentic RAG的核心差异，突出agent的作用。"

#### A.1.1 事件-因果知识图谱（EC-RAG）

**事件序列与因果链：**

```
E1: 传统RAG工作流程
  前置状态: 用户提出查询
  事件描述: 系统执行单次检索 → 将文档传递给LLM → 生成答案
  后置状态: 返回一次性答案
  [:TEMPORAL_NEXT] → E2

E2: 传统RAG的局限性识别
  前置状态: 单次检索完成
  事件描述: 讲者指出"如果初始检索质量不佳，整个流程失败"
  后置状态: 引入改进需求
  [:CAUSES] → E3

E3: Agentic RAG核心概念引入
  前置状态: 传统RAG局限性明确
  事件描述: 讲者介绍"Agent可以迭代决策和自适应调整"
  后置状态: 新范式建立
  [:TEMPORAL_NEXT] → E4

E4: Agentic RAG迭代机制
  前置状态: Agent接收查询
  事件描述: Agent执行循环
    1. 评估当前信息充分性
    2. 决定是否需要更多检索
    3. 调整检索策略（重新表述查询、改变检索目标）
    4. 整合新信息
  后置状态: 达到信息充分阈值或最大迭代次数
  [:CAUSES] → E5
  [:FEEDBACK_LOOP] → E4 (自循环)

E5: Agent工具使用
  前置状态: Agent决策需要工具
  事件描述: 讲者演示LangGraph、LlamaIndex Workflows
  后置状态: 工具集成到Agent工作流
  [:ENABLES] → E4

E6: 对比总结
  前置状态: 两种方法都已阐述
  事件描述: 
    - 传统RAG: "单程票"（one-way trip）
    - Agentic RAG: "反馈循环"（feedback loop）
    核心差异: 静态 vs 动态、被动 vs 主动
  后置状态: 概念对比完成
```

**因果关系图：**

```
E2(局限性) --[:CAUSES]--> E3(引入Agent)
E3(新范式) --[:ENABLES]--> E4(迭代机制)
E5(工具) --[:ENABLES]--> E4(迭代执行)
E4 --[:FEEDBACK_LOOP]--> E4 (关键！迭代循环)
```

**EC-RAG生成的答案：**

> 传统RAG和Agentic RAG的核心差异在于**工作流程机制**：
>
> **传统RAG**采用**单次线性流程**：
>
> 1. 接收查询 → 2. 检索相关文档 → 3. 传递给LLM → 4. 生成答案
>
> 这是一个"单程票"过程，如果初始检索质量不佳，整个流程失败，没有纠错机制。
>
> **Agentic RAG**采用**迭代自适应流程**：
>
> 1. Agent接收查询
> 2. **反馈循环**：
>    - 评估当前信息是否充分
>    - 如果不足，重新表述查询或调整检索策略
>    - 整合新检索的信息
>    - 重复直到满足条件
> 3. 基于完整信息生成答案
>
> **Agent的作用**：
>

- ✅ 深度：强调"反馈循环"这一核心机制
- ✅ 密度：具体工具名称（LangGraph、LlamaIndex）

#### A.2.2 事件-因果知识图谱（EC-RAG）

**事件序列：**

```
E1: 产卵与受精阶段
  前置状态: 繁殖季节到来
  事件描述: 雌性在地面产卵 → 雄性受精 → 雄性守卫
  后置状态: 受精卵开始发育
  [:TEMPORAL_NEXT] → E2

E2: 孵化触发运输
  前置状态: 卵孵化为蝌蚪
  事件描述: 蝌蚪背部黏液分泌 → 雄性将其背负
  后置状态: 蝌蚪附着在雄性背部
  [:CAUSES] → E3

E3: 运输到凤梨植物
  前置状态: 蝌蚪在雄性背上
  事件描述: 雄性攀爬到树冠层 → 寻找凤梨植物积水池

  后置状态: 蝌蚪需要食物来源
  [:CAUSES] → E5

  前置状态: 蝌蚪饥饿

  后置状态: 蝌蚪获得营养，继续生长
  [:FEEDBACK_LOOP] → E5 (每3-5天重复)
  [:TEMPORAL_NEXT] → E6

E6: 巡视与应急转移
  前置状态: 积水池可能干涸
  事件描述: 雄性检查水位 → 如果不足，转移蝌蚪
  后置状态: 蝌蚪在新的安全环境
  [:TEMPORAL_NEXT] → E7

E7: 变态完成
  前置状态: 蝌蚪发育成熟
  事件描述: 变态为幼蛙 → 离开积水池
```

```
E1(产卵) --[:CAUSES]--> E2(孵化)
E2(孵化) --[:TRIGGERS]--> E3(运输)

```

> 箭毒蛙的幼仔照顾是一个**时序因果链**：
>
> **阶段1：产卵与守卫**
>
> - 雌性产卵 → 雄性受精 → 雄性守卫孵化
>
> **阶段2：孵化触发运输**
>
> - 卵孵化为蝌蚪 → 蝌蚪分泌黏液 → 雄性将其背负
> - **因果关系**：孵化是运输的触发条件
>
> **阶段3：运输到树冠**
>
> - 雄性攀爬到树冠层 → 寻找凤梨植物积水池
>
> **阶段4：放置创造营养需求**
>
> - 蝌蚪放入积水池 → 开始独立生活 → **引发营养需求**
>
> **阶段5：营养供给循环（关键机制）**
>
> - 雌性定期返回 → 产下未受精卵 → 蝌蚪摄食 → 生长
> - **反馈循环**：每3-5天重复一次，持续6-8周
> - **因果逻辑**：营养供给是蝌蚪存活的必要条件
>
> **阶段6：应急响应**
>
> - 雄性巡视发现水位下降 → 转移蝌蚪到新地点
> - **因果触发**：环境变化驱动父母行为调整
>
> **整体流程**：产卵 → 孵化 → 运输 → 放置 → **循环供养** → 变态

- ❌ 全面性：缺少"环境选择"行为（雌性评估积水池）
- ❌ 全面性：缺少"父母合作"的明确描述
- ⚠️ 深度：强调了时序和因果，但角色分工不清晰
- ⚠️ 密度：流程完整，但缺少"谁负责什么"的细节

**关键差异分析：**

| 维度     | 实体图                    | EC-RAG（因果图）                |
| -------- | ------------------------- | ------------------------------- |
| 行为覆盖 | ✅ 8个行为全部列出        | ❌ 遗漏"环境选择"和"合作"       |
| 角色分工 | ✅ 明确"雌性做X，雄性做Y" | ❌ 只说"雄性运输"，雌性角色模糊 |
| 并行关系 | ✅ 同时进行的任务清晰     | ❌ 强制线性化为时序链           |
| 细节密度 | ✅ 频率、数量、时长具体   | ⚠️ 只有大致流程               |
| 适用查询 | ✅ "做什么"/"谁负责"      | ✅ "为什么这样做"/"流程是什么"  |

**为什么实体图在此场景胜出：**

1. **问题类型是枚举型**："如何照顾"要求列举所有行为，不是因果推理
2. **并行关系重要**：雌性和雄性同时有不同职责，不是严格的时序依赖
3. **静态描述充分**：行为本身的描述比"为什么这样做"更重要
4. **实体图的结构优势**：`Actor --[:PERFORMS]--> Action` 关系天然适合回答"谁做什么"

## Appendix C: EC-RAG Implementation Details

This appendix provides the technical implementation details of the Event-Causal RAG (EC-RAG) framework used in our experiments, adapted from Yan et al. (2026).

### C.1 Algorithm Pseudocode

The EC-RAG pipeline consists of three main phases: (1) Perception Layer for video chunking, (2) Cognition Layer for SES graph construction, and (3) Retrieval & Generation with deduplication.

```
Algorithm 1: EC-RAG Construction and Retrieval
Input: Video V, Vision encoder Ψv, VLM, Embedder Ψe, Query Q
      ASR Speech Islands A, Thresholds τevent, τbg, γ, τdup
Output: Event-Causal Knowledge Graph G, Answer A

// Phase 1: Dual-Modal Sentinel Chunking
B ← ∅, C ← ∅
for each frame ft ∈ V do
    vt ← Ψv(ft)              // Extract vision features
    B ← B ∪ {vt}
  
    if |B| ≥ 2 then
        // Compute smoothed visual dissimilarity
        Dsmooth(t) ← GaussianFilter(1 - cos(vt-1, vt))
  
        if Dsmooth(t) > τevent and is_local_maximum then
            tcore ← t        // Core event boundary
    
            // Expand boundaries using background threshold
            tstart ← TraverseBack(tcore, until Dsmooth < τbg)
            tend ← TraverseForward(tcore, until Dsmooth < τbg)
    
            // Align with speech islands (audio modality)
            for each speech island [tas, tae] ∈ A do
                if [tas, tae] ∩ [tstart, tend] ≠ ∅ then
                    tstart ← min(tstart, tas)
                    tend ← max(tend, tae)
    
            C ← C ∪ {Sample(V[tstart:tend], 8.0 FPS)}

// Phase 2: SES Graph Construction & Merging
G ← ∅, Sprev ← NULL
for each chunk c ∈ C do
    // Generate State-Event-State triple via VLM
    SESc ← VLM.Generate(c, Prompt_SES)
    G ← G ∪ SESc
    Insert SESc to VectorDB
  
    // Merge adjacent chunks via state alignment
    if Sprev ≠ NULL then
        vpost ← Ψe(Sprev.Post_State)
        vpre ← Ψe(SESc.Pre_State)
  
        if cos(vpost, vpre) > γ then
            Create edge: Sprev --[:TEMPORAL_NEXT]--> SESc

    Sprev ← SESc

// Phase 3: Retrieval & Generation with Deduplication
Anchors ← VectorDB.TopK(Ψe(Q), K=3)
Mseen ← ∅, Ctx ← ∅

for each anchor a ∈ Anchors do
    SubGraph ← GraphDB.BFS(a, MaxHops=2)
  
    for each node n ∈ SubGraph do
        // Deduplication via semantic similarity
        if Mseen ≠ ∅ then
            Smax ← max{cos(Ψe(n.Text), v) | v ∈ Mseen}
        else
            Smax ← 0
  
        if Smax ≤ τdup then
            Ctx ← Ctx ∪ {n.Text}
            Mseen ← Mseen ∪ {Ψe(n.Text)}

A ← LLM.Generate(Q, Ctx)
return A
```

**Key Parameters:**

- `τevent = 0.72`: Event boundary detection threshold
- `τbg = 0.60`: Background stability threshold
- `γ = 0.75`: State alignment threshold for temporal merging
- `τdup = 0.85`: Deduplication threshold to avoid redundant context
- Sampling rate: 8.0 FPS for selected chunks

### C.3 Dual-Store Retrieval Strategy

EC-RAG employs a **hybrid retrieval strategy** combining vector similarity and graph traversal:

**Vector DB (Semantic Matching):**

- Embedding model: `text-embedding-3-large` (OpenAI) or equivalent
- TopK = 3 anchor nodes retrieved based on cosine similarity
- Serves as entry points for graph traversal

**Graph DB (Topological Expansion):**

- BFS traversal from each anchor, MaxHops = 2
- Follows edges: `[:TEMPORAL_NEXT]`, `[:CAUSES]`, `[:ENABLES]`, `[:FEEDBACK_LOOP]`
- Collects connected SES triples for comprehensive context

**Deduplication:**

- Compute pairwise similarity between all retrieved nodes
- Threshold τdup = 0.85 filters near-duplicate content
- Reduces token cost while maintaining information coverage
